Situation:
"I was setting up a multi-service Docker Compose stack — a React/Vite frontend, a Go backend, and Postgres — for a project called DevBoard. The database and backend came up fine, but the frontend container failed immediately with a cryptic error: /bin/sh: Syntax error: Unterminated quoted string. There was no obvious quote issue anywhere in my Dockerfile or package.json."
Task:
"I needed to figure out why a container that should just run vite was instead being interpreted as a broken shell script, without introducing a fragile workaround."
Action:
"I worked through it systematically rather than guessing. First I ruled out the compose file and package.json — the CMD was in exec form, so no shell parsing should even happen there. That led me to suspect the contents of the container itself were corrupted rather than the command. My hypothesis: my Dockerfile did COPY . . after npm install, and without a .dockerignore, my local macOS node_modules — including a platform-specific vite binary — was getting copied on top of the Linux-built one inside the container. When the shell tried to execute that Mac binary on Linux, it couldn't run it as a binary, so it fell back to reading it as a shell script, and choked on quote characters inside the JS.
To fix it properly instead of patching around the symptom, I restructured the Dockerfile into a multi-stage build: a -dev build stage that installs dependencies and runs the Vite build, and a minimal runtime stage that only copies over the built output. I also switched ENTRYPOINT/CMD to exec-form arrays so the container invokes vite directly through node, bypassing the shell entirely — which eliminates this whole class of quoting bugs. I added a .dockerignore excluding node_modules so host-built artifacts could never leak into the image again."
Result:
"The frontend came up cleanly, and the fix also happened to harden the setup — smaller runtime image, no host/container platform mismatches possible, and no shell-parsing surface for that kind of error to recur. It was a good reminder that a confusing error message is often a symptom one layer removed from the real cause, and that fixing the underlying mechanism (shell dependency, missing .dockerignore) beats patching the specific symptom."
